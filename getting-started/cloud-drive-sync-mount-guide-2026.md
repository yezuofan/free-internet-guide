# Google Drive 一直转圈、OneDrive 卡在「正在处理更改」：海外网盘同步与挂载分层排查指南（2026）

**2026 年 10 月更新。** 一个 3.8GB 的工程包传到 78% 停住，进度条归零重来；OneDrive 状态栏写着「正在处理更改」，一写就是一天；Dropbox 图标永远在转，重启一次能好五分钟。这些场景里，测速软件往往跑得很漂亮。云盘同步的瓶颈和看视频完全不是一回事——它怕的不是带宽不够，而是**请求太多、上行太窄、长连接被掐，以及几层容易被忽略的中间环节**。

## 太长不看版

| 症状 | 大概率卡在哪 | 一句话 |
|:---|:---|:---|
| 网页能打开，客户端一直「正在连接」 | 第三层：客户端没真正走代理 | 浏览器通 ≠ 客户端通 |
| 卡在「正在处理更改」「正在扫描」 | 第六层：元数据与校验，不是传输 | 它在数文件，不在传文件 |
| 几千个小文件传不完，单个大文件反而快 | 第二、五层：请求数 | 慢在握手，不在带宽 |
| 上传到九成断掉重来 | 第二、四层：上行 + 断点续传 | 上行是短板，重传是代价 |
| 下午正常，一到晚上就卡 | 第四层：晚高峰 | 国际链路有潮汐 |
| 换成挂载盘后能拖进度条，但一拖就缓冲 | 第五层：缓存策略没配对 | 挂载不是同步 |

一句话：**同步盘怕的是「延迟 × 请求数」，不是带宽。**

## 一、先把三种「网盘」分清

同一个品牌名字，下面常常是两三种不同的东西，排查顺序也不同。混着查就是白折腾。

| 形态 | 典型代表 | 连接模式 | 对链路的要求 | 典型症状 |
|:---|:---|:---|:---|:---|
| **网页版** | 浏览器里打开云端盘 | 短连接 + 偶发大文件流 | 能打开、能续传 | 页面转圈、下载断流 |
| **同步盘** | Google Drive 桌面版、OneDrive、Dropbox、坚果云 | 常驻长连接 + 双向实时镜像 | 延迟低、请求数扛得住、上行够 | 卡「正在处理更改」、反复重连、版本冲突 |
| **挂载盘** | rclone mount、WebDAV 挂载 | 本机文件系统转发（FUSE / Dokan） | 低延迟 + 缓存策略 | 能打开但一操作就卡 |

网页版是一次性买卖：请求、下载、结束，断了重来也就重来那一个文件。同步盘是常驻合同：一直保持连接、持续监听本地改动、给每个文件算一次校验和，再和小得可怜的一批批请求慢慢磨——文件体积不大，请求数可以大到你想象不到。挂载盘则是把远端当本地磁盘用：你拖动视频进度条，等于要求立刻从文件另一个位置取数据，默认参数下顺序播放没问题，一拖就现原形。

三种形态里，同步盘对网络最挑，也最容易让人误判成「网速不行」。

## 二、为什么同步盘比看视频更挑线路

**一，它发的是海量小请求，不是一条大流量。** 每个文件至少要跟服务端对齐元数据、算校验和、开一条传输；几千个小文件就是几千轮对话。跨国往返一次 150 毫秒起，几百毫秒也不稀奇，几千轮排下来一上午就没了。带宽再大也压不下去，瓶颈在排队次数。

**二，它是常驻长连接。** 网页断了刷新一下就好，同步盘断了要走重连加重新比对的完整流程，链路抖一下，刚建立的状态全部推翻。

**三，同步主要吃上行。** 本地新建一个 500MB 素材包要推上去，而家用宽带下行标几百兆、上行常常只有下行的十分之一——套餐写「1000M」，上行给的可能是 50M 甚至 30M。测速软件默认测下行，数字自然漂亮。

**四，跨国路径有潮汐。** 晚八点到十一点国际出口最堵，丢包一上来触发重传，重传又加剧拥堵。「白天同步挺快」说的正是这件事。

**五，服务器风控也会参与。** 一个出口 IP 上突然冒出几百条并发，服务端当异常流量限速，客户端只会显示「正在重试」。这也是少数人「加了参数反而更慢」的原因。

## 三、六层排查：从下往上

**第一层，域名解析。** 海外域名用本地运营商 DNS 解析，慢和错都是常事。解析要等好几秒就换公共 DNS，但要记住：**改 DNS 只解决「不知道去哪」，解决不了「路太远」**。它能把「打不开」变成「能打开但慢」，仅此而已——这也是「改 DNS 大法」被传滥的原因。

**第二层，传输协议。** 现在的客户端大量使用基于 UDP 的 QUIC / HTTP/3，而 UDP 在国内链路上待遇比较差：有的线路对它限速，有的干脆丢弃，客户端不报错，只会悄悄回退或反复重试，表现就是「能连上、就是慢」。找找客户端有没有「禁止 QUIC」「仅使用 TCP」这类开关，打开对比一次；换条线路症状变化，就说明问题在路径上。大文件上传还牵扯包尺寸——隧道封装吃掉几十个字节后，装满的包被静默丢弃，症状正好是「传到某个百分比就断」。

**第三层，客户端到底有没有走代理。** 这是最高频的坑。系统代理只覆盖一部分应用：读系统设置的应用会走，自己实现网络栈的（命令行工具、后台服务、部分同步客户端）不走。所以「浏览器能开、客户端一直正在连接」这种自相矛盾的现象，九成出在这一层。客户端里能填代理就填一次；或者直接开 TUN / 虚拟网卡模式，让流量在网络层被接管。

命令行工具通常认环境变量：

```bash
export HTTPS_PROXY=http://127.0.0.1:7890
export HTTP_PROXY=http://127.0.0.1:7890
export NO_PROXY=localhost,127.0.0.1
```

设完**要重开终端**；以服务方式跑的要重启服务，光重启终端不够；用 systemd 起的后台任务得把变量写进 unit 文件，命令行 `export` 对服务无效。这一步最容易漏。

**第四层，上行带宽。** 别只看下行数字，上行单独测。上行只有二三十兆的话，传一个 20GB 素材包理论上就得十几分钟起步，还要用掉一部分做协议开销和重传。这一层没法优化，只能避开：把大包传输安排在本地网络空闲时段、传前停掉系统更新与自动备份、上行确实不够时把「同步盘」换成「挂载盘 + 按需下载」。

**第五层，并发与限速设置。** 默认值大多偏保守，而限速经常是自己误开的：

- **传输连接数 / 并行数**：调高能提升小文件整体吞吐，太高会被服务端限流，从默认往上走一档实测
- **客户端自带限速**：OneDrive、Dropbox、MEGA 设置里都有上传/下载速率限制，填 0 或取消勾选才是不限。有人当初为「不影响开会」限成 500KB/s，之后半年都在抱怨同步慢
- **缓存策略（挂载）**：这是挂载盘能不能用的分水岭。默认几乎不缓存，一读就现拉；打开缓存后顺序读明显改善，代价是本地占空间

**第六层，服务端状态。** 上传前要算校验和做「秒传」判断，本地 CPU 一忙进度条就不动。另外几种典型情况：共享盘/团队盘的配额、权限、成员并发都在服务端，客户端显示卡住其实是在等响应；回收站与版本历史占满配额，上传被静默拒绝；同一文件在两台设备改过会生成冲突副本，越积越多，每次扫描都变慢；账号本身被限流（并发太高、出口 IP 频繁变化都会触发）。判定办法只有一个：**换一个干净账号、传一个小文件**。能过就是服务端侧。

## 四、四大网盘的具体差异

| | Google Drive | OneDrive | Dropbox | MEGA |
|:---|:---|:---|:---|:---|
| **形态** | 桌面版（流式 / 镜像两种模式） | 桌面版 + 文件按需 | 桌面版 + 选择性同步 | 桌面版 + 端到端加密 |
| **代理** | 走系统代理 | 跟随系统，可单独设 | 客户端里可手动指定 | 客户端内建代理（支持 SOCKS5） |
| **并发相关** | 大文件分片上传，分片可调 | 同步引擎并发由客户端管 | 有下载/上传速率设置 | 传输连接数 + 限速都可调 |
| **典型卡点** | 分片偏小、大文件反复重传 | 大量小文件扫索引（「正在处理更改」） | 局域网同步没用上、反复重连 | 客户端加密吃 CPU、限速被误设 |
| **隐藏设置** | 流式 / 镜像决定本地是否全量落地 | 「文件按需」决定本地占不占空间 | LAN 同步在同网段设备间可省流量 | 连接数默认保守，多线程要手动加 |

- **Google Drive 两种模式要选对。** 镜像模式把云端全部落地，本地磁盘直接翻倍；流式模式只放占位符，但每次打开都走网络——首次打开慢不是故障。
- **OneDrive 的「正在处理更改」基本都是在扫索引**，不是在传文件，文件几十万、目录层级深的时候可以持续很久。缩小同步范围、排除开发目录、别把同步根放在外接移动硬盘上。
- **Dropbox 在同一局域网内的设备之间可以直连同步**，走本地网速，默认开着但经常被忽略；两台设备明明在同一间办公室还慢速同步，就检查这个开关。
- **MEGA 的传输是客户端加密的**，每块数据都要在本机加解密，CPU 弱的老机器上瓶颈不在网络在处理器。另外它的限速单位是 KB/s，填错一个数量级就慢得毫无理由。

## 五、挂载实操：rclone 最小可用配置

不想让几 TB 数据全部落地，又想在资源管理器里当本地盘用，最通用的方案是 rclone：支持的云存储上百种，配置是一个纯文本文件，好备份好迁移。

```bash
rclone config
# n 新建 → 起名（如 gd）→ 选类型（drive / onedrive / dropbox / mega）
# OAuth 类型选 Auto config，会自动拉起浏览器授权
rclone lsd gd:      # 能列出目录就说明配置成功

rclone mount gd: /mnt/gd \
  --vfs-cache-mode full \
  --vfs-cache-max-size 20G \
  --buffer-size 64M \
  --dir-cache-time 12h \
  --read-ahead 128M \
  --transfers 8 \
  --checkers 16 \
  --contimeout 30s \
  --retries 5 \
  --low-level-retries 20 \
  --daemon
```

各参数管什么：

| 参数 | 作用 | 建议 |
|:---|:---|:---|
| `--vfs-cache-mode full` | 读写都缓存到本地 | 要用挂载就开这个，默认几乎等于不用 |
| `--vfs-cache-max-size` | 缓存上限 | 按本地空闲磁盘给，别不给上限 |
| `--buffer-size` | 每个文件的内存缓冲 | 注意占用是「每文件」，大文件多就调大 |
| `--dir-cache-time` | 目录列表缓存时长 | 冷数据调长，省的是元数据请求 |
| `--read-ahead` | 顺带预读 | 顺序播放明显受益 |
| `--transfers` / `--checkers` | 并行传输 / 并行检查 | 默认偏保守，往上调一档实测 |
| `--contimeout` / `--retries` / `--low-level-retries` | 超时与重试 | 跨国链路必调，默认值在抖动路径上很容易失败 |
| `--bwlimit` | 限速 | 平时别开，要给会议留余量时才临时加 |

配置文件默认在 Windows 的 `%APPDATA%\rclone\rclone.conf`、Linux 与 macOS 的 `~/.config/rclone/rclone.conf`，纯文本。代理优先用环境变量；部分子命令也支持直接指定代理参数，但版本间有差异，用 `rclone help flags | grep -i proxy` 查当前版本认不认，别照抄别的文章。

**「拖进度条会卡」是物理代价，不是参数问题。** 顺序播放是预读的主场，随机跳转才是考试：拖动的瞬间播放器要求立刻从另一个位置取数据，默认缓存下只能现拉，往返 200 毫秒就够播放器停下来缓冲。加大预读和缓存上限能缓解，不能根治。

**有三种活别用挂载干**：数据库文件、剪辑素材盘、编译目录。它们对随机读写和写入原子性有要求，挂载层只保证「看起来像本地盘」，不保证「行为像本地盘」——定时同步能把 checkpoint 传坏，挂载跑数据库会在崩溃后留下半截数据。

## 六、上传下载分开提速

**小文件多的时候，打包比调参有效得多。** 一千个 50KB 的文件就是一千轮握手加一千次校验，压成一个包只剩一轮；这是唯一能把请求数从上千降到个位的办法。代价是断点续传粒度变粗，所以大包最好配合分卷。

**大文件反过来简单**，瓶颈通常是上行和分片参数：调大分片、开多线程流能吃到更多带宽，但别指望超过上行上限。

**排除规则一定要写。** 至少排除 `node_modules`、`.git`、构建产物、系统缓存、虚拟磁盘文件——它们的共同特点是数量巨大、单体很小、天天变、重新生成成本低。

**限速检查两遍。** 自己的客户端限速是第一大隐形杀手，第二是路由器上几年前为「打游戏不卡」设的历史 QoS 规则。

**断点续传必开。** 传到九成断掉、进度归零重来最消耗耐心；续传参数在跨国链路上要给宽松一点，默认超时和重试次数在抖动路径上很容易直接判失败。

**校验和 / 秒传不是免费午餐。** 上传前要算哈希，几十 GB 算一遍要时间，进度条会卡在「准备中」；省的是重复上传，花的是 CPU 和等待。

## 七、多端与共享的几个坑

- **手机端在蜂窝网络下容易被系统限制后台联网**，表现是「打开 App 才开始传」。改成手动触发或只在 Wi-Fi 下同步，反而省心。
- **NAS 和同步盘混用要小心**：NAS 上跑同步客户端会生成大量小文件和临时文件，再被另一个同步任务扫一遍，很快进入「一直在处理」的死循环。要么 NAS 只做挂载，要么把同步范围划得极清楚。
- **共享盘卡往往和链路无关**：成员多、并发高、权限复杂，服务端响应慢，客户端只显示「同步中」。先看是不是只在你一个人身上慢。
- **出口 IP 频繁变化会让账号进风控**：上午家里、下午公司、晚上手机热点，服务端看到的是三个地区的登录环境，验证、限流、临时冻结都会跟上来。要让账号稳定，**出口归属的一致性比速度重要得多**。

## 八、选线路时看三个观察点

1. **上行给多少。** 同步盘吃上行，供应商却几乎只宣传下行。办之前问清楚，或拿一个几 GB 的文件真跑一次。
2. **延迟和抖动，而不是峰值速度。** 晚八点到十一点测一次实际延迟，比看任何标称带宽都有用。
3. **出口归属是否长期稳定。** 多设备、多账号场景里，这条比速度更重要。

## 九、开工前自查清单

1. 网页能开、客户端不行 → 先查代理覆盖，别重装客户端
2. 上行单独测一次，别只看下行数字
3. 传输前停掉系统更新、自动备份、其他同步任务
4. 小文件先打包再传，把请求数降下来
5. 取消客户端自带限速，顺手检查路由器有没有历史 QoS 规则
6. 大文件确认断点续传开着，超时与重试调宽
7. 同步范围缩小：排除 `node_modules`、`.git`、构建产物、缓存目录
8. 多设备账号场景，出口归属保持前后一致
9. 挂载盘不要用来跑数据库、剪辑、编译
10. 关键传输安排在本地网络空闲时段，别硬撞晚高峰

## 十、FAQ

**Q：测速跑满，云盘还是慢，是测速软件坏了吗？** 不是。测速测的是下行峰值，同步吃的是上行、延迟和请求数，三者可以完全不相关。

**Q：改 DNS 之后确实快了一点，还需要管别的吗？** 改 DNS 只影响「去哪儿找」，路本身绕、本身堵，它管不了。只是「快了一点」，说明问题没解决。

**Q：同步卡在「正在处理更改」几天了怎么办？** 它多半在扫元数据和算校验和，不是卡在传输。文件太多、目录太深、把开发目录也同步进去都会让这步无限长，缩小同步范围比换线路有效。

**Q：挂了代理，命令行工具怎么还是连不上？** 命令行不走系统代理。要么设 `HTTPS_PROXY`（设完重开终端，服务跑的要重启服务），要么开 TUN 模式在网络层接管。

**Q：rclone 挂载能当本地硬盘用吗？** 读为主可以，写要谨慎。看文档、看视频没问题；数据库、剪辑素材盘、编译目录别放上面。挂载层模仿的是文件系统接口，不是它的行为。

**Q：换一条线路症状就消失，能说明原线路不行吗？** 能。同一账号、同一批文件、同样参数，换条路径就好，说明瓶颈在路径上（延迟、抖动、UDP 待遇、出口拥堵），而且可以反复验证。

**Q：多设备同步总互相覆盖，是网络问题吗？** 基本不是。同一文件在两台设备改过，客户端要生成冲突副本再比对，先解决流程问题——约定谁改哪个目录、文档类换到带版本历史的协作工具。网络只会把这类问题放大。

**Q：同步盘和挂载盘该用哪个？** 看数据要不要落地。要随时打开、离线可用，用同步盘；几十上百 GB、本地放不下、只要「能访问」，用挂载盘。混着用最糟，两套机制互相干扰。

## 十一、三句话总结

**第一，同步盘怕的是请求数、上行和长连接，不是峰值带宽。** 测速数字漂亮说明不了什么。

**第二，客户端不通，先怀疑代理覆盖那一层。** 浏览器能开、客户端不能开，这个矛盾九成出在那里。

**第三，参数能调，路径调不了。** 打包、清场、错峰、换线路——这四件事比任何调参都有效。
