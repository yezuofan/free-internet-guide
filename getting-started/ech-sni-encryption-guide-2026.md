# ECH 科普：HTTPS 都加密了，为什么还看得出你在访问哪个网站

> 原文：https://huanghaiwan.com/posts/ech-sni-encryption-guide-2026/

浏览器地址栏的小锁只承诺了一件事：你和网站之间传输的内容别人看不懂。它没有承诺——你访问了哪个网站别人不知道。这两句话之间的差距，就是 ECH 要解决的问题。

**一句话结论：** HTTPS 加密的是内容，TLS 握手第一阶段的 SNI（你要访问的域名）一直是明文。ECH 用「内外双层 ClientHello」把真实域名包进加密内层，外层只留一个 CDN 公开名称，让运营商和局域网监听者看不到你在访问哪个站点。2026 年它刚拿到正式标准编号（RFC 9849），安卓 17 也已在系统层面默认启用，但要真正用上，得服务端、客户端、加密 DNS 三段全部到位。

## 一、HTTPS 只锁内容，没锁「你要找谁」

TLS 握手最开始，你的设备发一条 ClientHello 报文，里面有个叫 SNI（Server Name Indication）的字段，内容是**明文的域名**。原因很实际：一台服务器挂了几千个网站、IP 只有一个，不告诉它你要访问哪个域名，它不知道该出示哪张证书。

于是中间任何一台设备只要愿意看，就能拿到一份清单：这个 IP 今天访问了哪些域名、什么时间、多频繁。运营商可以拿去做画像，公司网关可以拿去做审计，公共 WiFi 的中间设备可以拿去做重定向。内容看不到，行为轨迹一览无余。

让人不舒服的地方在于：这跟「有没有用 HTTPS」没关系。2026 年全球超过 95% 的网站都上了 HTTPS，浏览器还会给纯 HTTP 站点打「不安全」标签，用户因此形成「小锁 = 全私密」的印象，而 SNI 恰好落在这个印象的盲区里。有海外媒体直接把它叫做「最隐蔽的网络追踪漏洞」——它隐蔽，是因为绝大多数人根本不知道它存在。

## 二、ECH 的思路：套两层 ClientHello

- **外层 ClientHello**：给网络中间设备看的。里面只有一个「公开名称」（public name），通常是被广泛使用的 CDN 域名，比如 Cloudflare 用的 `cloudflare-ech.com`。监听者看到的只是「这个人在访问某 CDN」。
- **内层 ClientHello**：真正的握手内容，包括你实际要访问的域名、ALPN 等敏感字段。它用服务端公钥加密后塞进外层的扩展字段里，只有目标服务器能解开。

服务端解密内层、按真实域名出证书、继续握手。中间设备全程只看见一个和它无关的 CDN 名称。

公钥从哪来？靠 DNS。服务端的 HTTPS 记录（记录类型 65）里带一份 ECHConfig。这里有个容易被忽略的推论：**如果 DNS 查询本身是明文的，ECH 的收益会被抵消**——中间设备虽然解不开内层，但能在明文 DNS 响应里看到你解析了哪个域名，或者干脆改掉 HTTPS 记录让 ECH 降级失败。所以加密 DNS（DoH/DoT）算不上 ECH 的搭配功能，它是 ECH 生效的前提。

至于「服务端不支持怎么办」，ECH 也没摆烂：客户端会发送一个随机填充的 GREASE 版本，看起来和真 ECH 一模一样，服务端按普通 ClientHello 处理。监听者无法通过「有没有 ECH 就直接拒绝」来逼你说出真实域名——要么看到加密 ECH，要么看到无害的随机值。这个设计挡住的是降级攻击，比单纯的加密更关键。

2026 年 3 月，IETF 正式发布 **RFC 9849**，ECH 从实验性草案变成 TLS 1.3 的正式标准扩展。从提出讨论到定稿，这件事磨了差不多六年。

## 三、2026 年的进度：从浏览器试验到系统底层

| 时间 | 事件 | 为什么重要 |
|:----|:----|:----|
| 2026 年 3 月 | RFC 9849 正式发布 | 从草案变标准，厂商有据可依 |
| 2026 年 8 月 27 日 | 谷歌宣布安卓 17 在系统层面集成 ECH | 全球首个原生支持的移动操作系统 |
| 2026 年 8 月底 | Caddy 内置 ECH 支持的配置指南出现 | 自建站点的接入门槛降下来了 |
| 2026 年 9 月 | OpenSSL 4.0 的 ECH API 细节公开 | 底层库补齐，服务端软件会跟着铺开 |

在此之前，ECH 的支持基本停留在桌面浏览器层面，手机上则是「系统不支持、浏览器想开也开不了」。现在变成系统级默认行为，覆盖量级完全不是一个数量级。但别急着乐观：ECH 生效需要服务端、客户端、DNS 三段全部配合，任何一段掉链子就退回明文 SNI，而部署 ECH 需要服务端持有私钥、CDN 支持、密钥轮换这一整套维护工作。标准定稿和全网普及之间，通常还隔着好几年。

## 四、对跨境网络访问意味着什么

**挡得住**：中间设备通过读取明文 SNI 识别你要访问哪个域名。这类识别是很多网络管理手段的基础，不知道域名，基于域名的规则就无从下手。

**挡不住**：IP 地址。你连的还是那台服务器的 IP，目标 IP 是什么、流量多大、什么时候连的，全都看得见。如果中间设备掌握了 IP 与服务的对应清单，照样能推断。另外，明文 DNS 场景下 ECH 配置可被篡改，客户端会静默降级回明文 SNI，用户完全无感——这是目前最现实的风险面。

如果你走的是加密隧道，那你的全部流量早就被封在隧道里了，链路上的设备本来也看不到 SNI。ECH 的价值体现在别处：链路两端的接入段与出口段如果是直连，这段的明文 SNI 依然是暴露点；访问 CDN 承载的站点时，ECH 让「你访问的是哪个具体站点」变成「你访问了某 CDN」，颗粒度一下粗了。

反过来说也要讲清楚：**ECH 不是加速工具，不会让线路变快。** 它不改路由、不改节点质量、不改带宽。把它当速度优化去选购，方向就错了。

## 五、ECH 和 TLS 指纹不是一回事

| 维度 | ECH | TLS 指纹伪装 |
|:----|:----|:----|
| 保护对象 | 你要访问的域名（SNI） | 你「长什么样」（客户端特征） |
| 谁在看 | 网络中间设备 | 目标服务器 / 风控系统 |
| 识别依据 | ClientHello 里的明文字段 | 密码套件顺序、扩展列表、椭圆曲线等组合 |
| 常见术语 | RFC 9849、外层/内层 | JA3、JA4、uTLS |
| 解决手段 | 把域名加密 | 把 ClientHello 伪装成真实浏览器的形状 |

打个比方：ECH 是把你寄信时信封上的收件人地址涂黑；TLS 指纹伪装是把你走路的步态、身高、口音改成另一个人的样子。前者防路上的人，后者防收件人的身份核验。标准 TLS 库发出的 ClientHello 特征组合非常固定，服务器把密码套件顺序、扩展列表拼成一个哈希（JA3 是这套算法的名字，JA4 是改进版），一比对就知道对面是浏览器还是脚本——于是有了 uTLS 这类逐字段伪装成 Chrome 或 Edge 形状的库。两件事合起来才覆盖完整：域名被加密、客户端形状也像真浏览器。

## 六、怎么检查自己的连接有没有用上 ECH

| 平台 / 客户端 | 支持情况 | 前提条件 |
|:----|:----|:----|
| Firefox 桌面版 | 支持，最积极 | 开启 DoH（`network.dns.echconfig.enabled` 为 true） |
| Chrome / Edge 桌面版 | 支持 | 系统或路由器的 DNS 返回 HTTPS 记录 |
| 安卓 17 | 系统级支持 | 系统 DNS 走加密通道 |
| iOS / macOS Safari | 跟进中，覆盖不均衡 | 需加密 DNS |
| 服务端（CDN / 自建） | Cloudflare 等早已支持；Caddy、OpenSSL 4.0 补齐 | 配置 ECH 密钥 + 定期轮换 |
| 各类加速客户端 | 逐步跟进，各版本差异大 | 看客户端版本与内核实现 |

最快的检查方式是用在线检测页（Cloudflare 有专门的 ECH 检查页），浏览器地址栏不会为 ECH 亮任何标志。客户端这块不要想当然——同一个软件半年内的两个版本，ECH 与指纹伪装的支持情况可能完全不同，升级前看一眼更新说明比翻设置页靠谱。

## 七、给普通用户的现实结论

ECH 是一次真正补洞的标准化，但从「标准定稿」到「你用得上」有三道门槛：目标站点得部署、你的客户端得支持、DNS 必须加密。三样齐了，SNI 才算真正被锁进加密层；缺一样，就还是明文。

更值得记住的是边界：ECH 保护域名，不保护 IP；配合加密 DNS 才有意义；对加速链路的隧道内部没有影响。你每天真正会感受到差别的环节，其实在链路本身——出口稳不稳、晚高峰掉不掉速、有没有抗抖动的多路复用、设备够不够用。这几件事 ECH 一个都管不了，但比 ECH 更影响每天的心情。

## 八、常见问题

**1. 开了 ECH 就完全看不到我访问什么了？** 不是。域名被加密，但 IP 地址、连接时间、流量大小、访问频率依然可见。如果站点是独享 IP，或中间设备已掌握 IP 与服务的对应关系，推断依然成立。ECH 缩小了暴露面，没有消除它。

**2. ECH 和加密 DNS 是一回事吗？** 不是，但有依赖关系。加密 DNS 保护「你查了哪个域名」，ECH 保护「你访问了哪个域名」。只做前者，中间设备仍能从握手读到 SNI；只做后者，中间设备能从明文 DNS 读到你要查的域名，甚至篡改配置让 ECH 降级。两个一起用才闭环。

**3. 上了 ECH 会不会变慢？** 几乎没有感知。多出来的是握手阶段的一次加解密和一次 DNS 查询，相比页面加载量可以忽略。真正可能变慢的是「DNS 从明文切到加密」这一步，但那是 DoH 的成本，不是 ECH 的。

**4. 我需要为了 ECH 换服务吗？** 不需要。目前这属于协议和服务端层面的事情，服务商能左右的空间很小。真要作为选购参考，看客户端是否跟随现代 TLS 特性即可。

**5. ECH 会影响流媒体解锁或节点选路吗？** 基本不会。解锁取决于出口 IP 归属与线路质量，选路取决于客户端分流规则和目标 CDN 的调度，ECH 只改变握手阶段暴露什么信息，不改变流量走向。

## 九、总结

HTTPS 加密内容，ECH 加密「你要访问谁」。前者花了二十年才普及到 95%，后者刚拿到正式标准编号，还在早期。技术上它做得很漂亮：内外双层 ClientHello、GREASE 兜底防降级、密钥走 DNS 下发。2026 年这几步——RFC 9849 定稿、安卓 17 系统级启用、OpenSSL 4.0 补齐 API——说明它正在从浏览器的小众试验变成基础设施的一部分，但服务端部署率、DNS 加密覆盖率、客户端跟进速度，每一环都在拖后腿。

对我们这些每天要访问海外网站的人来说，正确的态度大概是：知道它解决了什么，也知道它没解决什么。它不改变链路质量，不替代分流规则，不给你更快的速度。真正每天影响体验的，还是线路本身稳不稳。
