# 虚拟机与容器网络加速配置指南 2026：VMware、VirtualBox、WSL2、Docker 里的系统怎么走对线路

> 原文：https://huanghaiwan.com/posts/vm-container-network-acceleration-guide-2026/

宿主机上一切正常，网页秒开。开一台虚拟机进去，或者进 WSL 拉个依赖、`docker pull` 一个镜像，进度条就停住不动了。ping 通，DNS 也解析得出，就是不下载。

**一句话结论：虚拟机不是应用，是另一台设备。** 你给宿主机配的那套东西跨不过那道网络边界——它的流量有自己的网卡、自己的 IP、自己的一套 DNS。WSL2 甚至直接把这句话甩在你脸上：检测到 localhost 代理配置，但未镜像到 WSL。

## 太长不看

| 你的情况 | 推荐方案 | 一次配置能覆盖 |
|:---|:---|:---|
| 就一台虚拟机（或 WSL2），懒得折腾 | 宿主机开 TUN 模式 | 所有 NAT 模式虚拟机 + Linux 本机容器 |
| 虚拟机之间要互通、要模拟真实局域网 | 桥接 + 旁路由做网关 | 桥接虚拟机 + 家里所有设备 |
| 只跑 `git`、`pip`、`npm` 这类命令行 | 环境变量代理 | 只覆盖认代理的程序 |
| 要长期稳定、懒得每次配 | 里面单独装客户端 | 只覆盖这一台 |
| 跑生产级 Docker、多容器编排 | 宿主机 TUN 或旁路由 | 全机容器一次接管 |

一条原则记住就够：**NAT 模式的虚拟机和 Linux 上的容器会被宿主机的 TUN 接管；桥接模式的不行，得靠网关。**

## 一、为什么宿主机配好了，里面的系统还是连不上

三层边界。

**网络栈独立。** NAT 模式下虚拟机的 IP 是 `192.168.x.x`（VMware 走 VMnet8）或 `172.x.x.x`（WSL2 默认）；桥接模式拿到的是你家路由器发的、和宿主机同网段的地址。无论如何，它有自己的路由表和 DNS。

**代理天生是应用级的。** 系统设置里的「代理」只是一份声明，认它的程序去用，不认的（大量命令行工具、Java 应用）该直连还是直连。虚拟机里连这份声明都没有。

**DNS 各配各的。** 宿主机用什么协议解析、有没有加密，虚拟机不知道。所以「宿主机正常、虚拟机里域名解析不出来」是常见组合。

## 二、三种网络模式决定流量走哪条路

| 模式 | 虚拟交换机 | 虚拟机看起来像谁 | 流量路径 |
|:---|:---|:---|:---|
| 桥接 | VMnet0 | 局域网里的一台独立电脑 | 虚拟网卡 → 物理网卡 → 真实交换机（二层，不过宿主机路由） |
| NAT | VMnet8 | 躲在宿主机后面的私网机器 | 虚拟网卡 → 宿主机 NAT → 宿主机网络栈 → 物理网卡 |
| 仅主机 | VMnet1 | 只能和宿主机说话的机器 | 不出宿主机 |

关键在流量路径那一列：**桥接是二层桥接，不经过宿主机参与路由转发**，所以宿主机开 TUN 也接不到它。NAT 的包要先进宿主机网络栈，TUN 就能接住——这是 NAT 模式被低估的好处。

判定口诀：虚拟机里 `ip a` 看到的地址和宿主机同网段 → 桥接；看到 `192.168.x`／`172.x` 且网关是宿主机的虚拟网卡 → NAT。

## 三、四条解法

**方案一：里面单独装客户端。** 最彻底，什么模式都能用，虚拟机的全部流量都被接管。代价是每台都要装一遍、每台都多占一个设备数、订阅到期还得挨个更新。只有一台长期虚拟机时反而最省心。

**方案二：宿主机开 TUN（最推荐）。** NAT 模式的虚拟机和 Linux 容器（默认在 `docker0` 网桥上，出容器后由宿主机内核路由）都在宿主机路由表里，TUN 网卡一次全接住。要做的只有：宿主机客户端开 TUN 模式 → 虚拟机保持 NAT → 重新测。缺点是对宿主机权限要求高一点，且管不到桥接模式的虚拟机。

**方案三：桥接 + 旁路由当网关。** 虚拟机必须用桥接时（模拟真实局域网、多机互访），把出口往前挪一步，挪到整张网的网关上。覆盖面是「整张网」而不是一台机器，以后加设备不用再配。代价是需要一台常开设备，还要动 DHCP 或逐台改网关。

**方案四：应用层代理（四个环境变量）。** 只跑命令行时最轻：

```bash
export http_proxy=http://127.0.0.1:7890
export https_proxy=http://127.0.0.1:7890
export all_proxy=socks5://127.0.0.1:7890
export no_proxy=localhost,127.0.0.1,::1,192.168.0.0/16,10.0.0.0/8
```

四个都要写：只设前两个会漏掉走 SOCKS 的程序；`no_proxy` 不写清楚，内网地址会被硬塞进代理。大小写各导一遍最省事。**它只覆盖 HTTP/HTTPS 和部分 SOCKS，SSH、UDP、BT 做种一律不管**——「浏览器能开但某些软件还是不行」就是这个原因。

## 四、分平台要点

**VMware**：虚拟机能上网但极慢时，先确认 Windows 的「VMware NAT 服务」在跑，很多情况是它没起来或被安全软件拦了。走方案二不用动网卡设置。

**VirtualBox**：默认 NAT 会**截获虚拟机发出的 DNS 请求（53 端口）**转发给宿主机，你在里头配的加密 DNS 可能根本不生效。两种应对：换成「NAT 网络」，或 `VBoxManage modifyvm "虚拟机名" --natdnshostresolver1 off`。「虚拟机里 DNS 死活不生效」八成是这条。

**WSL2**：`%UserProfile%\.wslconfig` 里写 `networkingMode=mirrored`，镜像模式共享 Windows 网络接口和 localhost，宿主机代理与 TUN 直接生效、端口也不用转发。需要 Windows 11，改完必须 `wsl --shutdown` 才生效；早期是实验性功能，遇到兼容问题就切回 NAT 加环境变量。

**Docker**：`docker pull` 卡住，问题一定在守护进程层——**`dockerd` 不读 shell 环境变量，也不读 `~/.docker/config.json` 的 proxies 字段**，你在终端 `export` 完再 pull，一点用没有。正确位置是 systemd drop-in：

```ini
# /etc/systemd/system/docker.service.d/http-proxy.conf
[Service]
Environment="HTTP_PROXY=http://127.0.0.1:7890"
Environment="HTTPS_PROXY=http://127.0.0.1:7890"
Environment="NO_PROXY=localhost,127.0.0.1"
```

改完 `systemctl daemon-reload && systemctl restart docker`。另外镜像加速器只对 Docker Hub 官方镜像有效，私有 registry、`ghcr.io`、`quay.io` 都不走它。**顺序建议：先开 TUN 试，不行再逐层配代理**——反过来两套叠在一起，排查成本翻几倍。

**macOS（UTM / Parallels）**：Shared Network 就是 NAT，TUN 能接管；桥接在 macOS 上受系统网络权限限制，建议直接走方案三。

## 五、五个高频坑

| 坑 | 症状 | 怎么解 |
|:---|:---|:---|
| 虚拟机时钟漂移 | TLS 握手失败、证书报错，看着像网络问题 | 装 open-vm-tools / Guest Additions，开 NTP |
| NAT 模式没有入站连接 | BT/PT 做种传不动 | 桥接模式，或做端口转发 |
| DNS 两套各跑各的 | 宿主机正常，虚拟机解析失败 | 虚拟机内单独配，或旁路由统一接管 |
| 休眠后网络假死 | 显示已连接，什么都打不开 | 重启虚拟网卡服务 |
| 代理「看着生效实际没走」 | 配了变量、命令仍然慢 | 用出口 IP 核对，别信命令返回值 |

时钟那条值得单说：虚拟机长期挂起再恢复后时钟可能偏出几分钟，平时没事，偏得多 TLS 证书验证就失败，而报错文本通常像「连接被重置」，很容易误判成网络故障。

## 六、验收三步

不要用「能打开网页」当结论。浏览器有缓存也有重试，转几秒最后出来了，体验已经很难受但你分不出来。

1. **核对出口**：在虚拟机里（不是在宿主机里）访问查 IP 的接口，看归属地，再和宿主机比。两边不一致 = 流量还在直连。
2. **量三个指标**：对同一目标测延迟、丢包、抖动（mdev）。只看平均值没意义，要看波动。
3. **换到晚上再测一遍**：白天绿灯、晚八点后断续，是国际出口拥塞最典型的形态——配置没错，是这个时段就这样。

## 八、FAQ

**宿主机正常，虚拟机里 ping 通但下载不动？** ping 走 ICMP，小包能通只说明链路存在。跨境链路上「ping 通但速度上不去」最常见的原因是丢包——TCP 一遇丢包就砍发送窗口，ICMP 小包受影响小得多。

**宿主机开了 TUN，桥接的虚拟机为什么还是不行？** 桥接是二层，帧直接被物理网卡送进局域网，不经过宿主机路由转发；TUN 是三层的东西，接不到。

**一台订阅能在几台虚拟机里用？** 按台数算，虚拟机和你自己的电脑一样占名额。这也是方案二比方案一划算的原因——虚拟机与容器共享宿主机的出口，不增加设备数。

**WSL2 改镜像模式后还需要端口转发吗？** 不需要。但原来的 `netsh portproxy` 规则最好清掉，两份规则叠着会出现「一会儿能连一会儿不能连」。

**容器里配了 HTTP_PROXY 还是访问不了？** 先确认配的是哪一层。容器里的 `127.0.0.1` 指容器自己，不是宿主机。要么让代理监听 `0.0.0.0` 并配 `host.docker.internal`，要么直接用宿主机 TUN 接管容器流量。

## 最后

虚拟机里的网络问题，十次里有八次不是加速服务的问题，是「你没告诉它该怎么走」。

上手顺序：**先让虚拟机保持 NAT、宿主机开 TUN 试一次**，这一步能解决大部分人的问题、代价最小。不行再考虑旁路由网关，最后才钻进每一台里单独配。反过来先配一堆代理再开 TUN，两套东西叠在一起，出问题时排查成本会翻几倍。
