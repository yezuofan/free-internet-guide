# DeepSeek 图片功能全解 2026：识图是真的，生图是假的

**2026 年 10 月更新。** 搜「DeepSeek 图片」的人，一半是想让它画图。实测下来必须把两件事拆开：看懂你上传的照片，它做得到；把照片里的背景换成圣诞场景，它做不到。官方 API 到现在仍然只有「图进、字出」，没有文生图端点。这篇讲清它的图片能力边界、三种「能生图」说法的真相，以及三条真能出图的路子。

## 太长不看版

| 问题 | 短答 |
|:---|:---|
| DeepSeek 能生成图片吗 | 不能。官方只有图像输入（理解），输出永远是文字 |
| 现在该用哪个模型名 | `deepseek-flash`，对应 2026-09-10 发布的 V4.1 Flash（552B MoE） |
| 旧模型名还能用吗 | `deepseek-v4-flash-vision-exp` 还能调，但请求由 V4.1 Flash 承接，参数与计费都按新模型 |
| 网上说的「隐藏生图功能」 | 多数是插件或第三方模型在干活，画笔不在 DeepSeek 手里 |
| 想让它出图怎么办 | 三条路：当提示词工程师、API 串联、装插件 |
| 它最值钱的能力是什么 | 读图：报错截图、表格扫描件、UI 稿、图表读数 |
| 单图计费上限 | 每张图 1024 token，2000×2000 与 5000×5000 缩放后同价 |

## 一、能力边界：读图可以，画图不行

2026 年 9 月 10 日发布的 V4.1 Flash 是 552B 参数的 MoE，采用新的 Causal-Encoder-Decoder 结构，输入输出不对称，输入激活 8B、输出激活 16B；官方称 KV Cache 需求降到上一代四分之一、SSD 需求降到八分之一。这一代原生带视觉理解能力，官方文档的表述是：描述图片、识别截图文字、分析图表。

落脚点在这句话的最后两个字：**输出文字**。

判断一个模型能不能生图，最笨也最可靠的办法是翻端点列表。DeepSeek 这边有 `chat/completions`、`responses`、图片输入的 `image_url` 内容块，没有 `images/generations` 这类生成端点。没有端点，就没有生图。

常被翻出来的一张旧账：DeepSeek 实验室 2025 年 1 月开源过 Janus-Pro（7B / 1.5B），是正经文生图模型。开源模型存在，和对话产品里能画图，是两件事——它从没接进网页端、App 或付费 API。

## 二、三种「DeepSeek 生图」说法的真相

**一、别人晒的成品截图。** 图是真的，「这是 DeepSeek 画的」这句话无法验证。截图里看不到请求链路，也看不到背后是谁在渲染。

**二、插件与「装上画笔」。** 原理是把第三方生图模型包成工具或 MCP 服务，挂到 DeepSeek 的 agent 框架上。你说画只猫，模型调工具，工具去调别家接口，图回填进对话。链条通，但画笔不在 DeepSeek 手里。harness 开源后插件长出一大片，装之前先看清背后调哪家端点、密钥存哪、图传给了谁。

**三、两步法。** 先让 DeepSeek 把模糊需求扩写成生图模型能吃的描述，再贴到即梦、通义万相、Midjourney 的输入框里。这个流程真实有效，但属于「用它写文案」，不叫「用它画图」。

判断口诀只有一个：**看产物。出来是文字，就是文字模型在干活；出来是图片文件或图片链接，背后一定另有一个生图模型。**

## 三、路线 A：让它当提示词工程师

成本最低、效果最稳的一条。生图的瓶颈从来不是画技，是描述精度——写「一只猫」，给你一张平庸的猫；写「橘猫坐窗台，午后侧逆光，胡须边缘发亮，35mm 定焦，浅景深，背景虚化的绿植」，出来的东西能直接用。

固定指令模板（五段结构，每段一行）：主体与状态 / 材质与细节 / 光线方向与色温 / 焦段机位景深 / 风格画幅与排除项，最后单独给一行负向提示词。两个附加经验：语言按模型选（Midjourney 吃英文更准，即梦、通义万相、Qwen-Image 吃中文更自然），直接要双语省一轮翻译；输出要 JSON 不要散文，方便批量跑和换模型复用。

## 四、路线 B：API 串联，批量出图

骨架三步：文字模型产结构化描述 → 生图模型渲染 → 程序搬运落盘。

成本结构要算清楚：文字侧一次扩写几百 token，费用可以忽略；图片侧才是大头，国产文生图已有 0.18 元一张的档位，一百张就是十八块。所以优化重点是**重试率**，不是提示词省几个 token。三个工程坑：`response_format` 必须开，否则模型偶尔在 JSON 前后加一句客套话，解析当场炸；生图接口普遍限流，并发别开大；返回的图片链接有有效期，拿到就下载，别存 URL。

## 五、路线 C：插件与本地部署

不想把产品图、合同扫描件传给第三方的人走这条。harness 的「一切皆插件」架构就是为此设计：模型负责思考，框架负责执行，识图和生图作为插件挂上去。门槛在维护——插件质量参差，装之前看仓库最近提交时间，以及 issue 里有没有人报「图传出去回不来」。

## 六、识图才是真本事：五个用法与 API 变化

五个每周都在用的场景：报错截图直接扔进去；表格、发票、合同扫描件转结构化；UI 稿转 HTML；拍照翻译；图表读数（会自信地胡诌数字，必须交叉核对）。

API 侧 2026 年下半年才定型的变化，照老文章抄会踩：

- 传图三种方式：base64 data URL 内联、公开 http(s) 链接、Files API 的 `file_id` 复用。
- `detail` 四档：`low` 缩到 512×512 再推理，快且省；`high` / `original` 保留原图；`auto` 目前等同 `original`。
- **每图 token 上限 1024**，不是早期视觉预览版的 384。
- 请求体上限 48 MiB；单图 base64 或外链最大 32 MiB，`file_id` 可到 64 MiB；外链最长 8192 字符；单请求最多 600 张。
- 图片只能出现在 `user` 消息；塞进 `system` 或 `assistant` 直接 400。
- 北京时间工作日 9:00–12:00、14:00–18:00 是高峰，其余时段含周末全天半价。

## 七、五个照抄老教程必踩的坑

1. 写老模型名 `deepseek-v4-flash-vision-exp`（还能调，但已路由到 V4.1 Flash）。
2. 以为 `detail: high` 一定更贵（有 1024 封顶，4K 图与 2000 像素图费用差不了多少）。
3. base64 塞 40MB 的 PNG，编码后体积再涨三分之一，48 MiB 请求体当场爆。
4. 把图放进 system 消息，返回 400 且报错不解释原因。
5. 满世界找生图端点——找不到是正常的，它不存在。

## 收尾

DeepSeek 没有画笔，它有一双很好的眼睛和一张很会描述的嘴。想画图，把描述交给它，把落笔交给真正的生图模型——这个分工下，它依然是整个流程里最省时间的一环。
