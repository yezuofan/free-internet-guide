# 测速满格却打不开网页？MTU 与 MSS 科普：分片、PMTU 黑洞，以及隧道封装吃掉的那几十字节（2026）

**2026 年 10 月更新。** 有一种网络故障特别气人：测速跑满，首页能打开，图片加载到一半停住；换个网站，转圈转到天荒地老；下载大文件卡在 99%。你去 ping 一下——**通的**，一个包都不丢。于是开始怀疑运营商、怀疑线路、怀疑路由器。真正的元凶往往是一个你从没注意过的参数：**一个包最多能装多大**。

## 太长不看版

| 症状 | 大概率是什么 | 一句话 |
|:---|:---|:---|
| ping 通、小页面能开，图片视频就是加载不动 | 包尺寸超过链路能承载的上限 | 小包能过，大包消失 |
| 有的网站秒开，有的永远转圈 | 不同目标走不同路径，尺寸上限不同 | 是路径的问题，不是网站的问题 |
| 开了隧道或客户端加速后，部分站点开始打不开 | 封装多套了一层包头，可用尺寸被压小 | 隧道开销没算进 MTU |
| 握手卡住、大文件断在前面几兆 | 典型 MTU 不匹配，握手包刚好超标 | 改一次就好的那种 |
| 换成手机热点一切正常 | 那条路径的尺寸上限更宽松 | 反证问题在本级链路 |

一句话判断：**能 ping 通不等于没问题**。ping 默认发几十字节的小包，它恰好绕开了这个坑。

## 一、1500 是怎么来的：MTU 与 MSS 的 40 字节算术

**MTU 是一个接口一次能发出的 IP 包最大长度**，包含 IP 头本身。以太网的默认值是 1500 字节，从诞生沿用至今。

这 1500 字节不是全给数据。IPv4 头占 20 字节，TCP 头再占 20 字节，剩下 1460 才是 TCP 一次能带的数据量——这个数就是 **MSS**。

```
MTU 1500 = IP 头 20 + TCP 头 20 + TCP 数据 1460（MSS）
```

记住这层关系，后面全都能推出来：

| 环境 | MTU | MSS | 怎么来的 |
|:---|:---:|:---:|:---|
| 普通以太网 / 局域网 | 1500 | 1460 | 1500 − 20 − 20 |
| 家庭宽带 PPPoE 拨号 | 1492 | 1452 | 多套了 8 字节拨号头 |
| IPv6 链路 | 1500 | 1440 | IPv6 固定头 40 字节 |
| 常见隧道内 | 1420 或更低 | 1380 上下 | 外层封装又占掉几十字节 |

两个容易混的点：**MTU 是接口的属性，MSS 是 TCP 的属性**。前者是"这条路能过多大的车"，后者是"我们俩商量好每次拉多少货"。改 MTU 是改路，改 MSS 是改货。

至于为什么偏偏是 1500：以太网帧最大 1518 字节（14 帧头 + 1500 载荷 + 4 校验），1500 就是这个老规范里的数。它不是物理极限，纯粹是历史约定，而且约得相当成功——全世界的网卡、交换机、路由器都按它来。

## 二、PPPoE 为什么要减 8：1492 与 1452

家庭宽带用的 PPPoE 拨号，是在以太网之上又套了一层协议，占 **8 个字节**（6 字节 PPPoE 头 + 2 字节 PPP 协议字段）。以太网能装 1500，经这层包装后真正能承载的只有 **1492**，对应 MSS = 1492 − 20 − 20 = **1452**。

光猫或路由器 WAN 口如果还按 1500 配，每个"装满"的包都会超标 8 字节。测速软件用小包测、数字漂亮，实际使用全是满包、体验稀烂——很多人卡在这一步。

> 一句经验：**PPPoE 环境下 WAN 口 MTU 应该是 1492**，对应 MSS 1452。这是最常见的默认错误。

也要说清：情况在变化，部分地区已用上不经过 PPPoE 的接入方式，这时 1500 反而是对的。别背结论，**自己测一次**（方法见第五节），测出来多少就是多少。

## 三、包太大会怎样：分片这件事

IPv4 允许中间设备把过大的包"切开"再发，叫**分片**。听起来聪明，代价不小：

1. **每个分片都是独立小包**，各自占头部、各自排队，路由器开销上来；
2. **任一分片丢失，整个原始包都要重传**——丢一个小碎片，重传一整份数据；
3. **最后一片丢了最难受**，前面全收到就差一点，重组超时，全部白收。

所以真实网络里分片被视为"能不做就不做"。现代协议栈的做法是**在 IP 头打一个 DF 位（Don't Fragment）**，明确告知路上所有设备"不许切"。切不了怎么办？设备应该丢包并回一条通知，让发送方自己调小——这就是下一节。

## 四、PMTU 黑洞：设备想告诉你，但话被拦了

发送方设了 DF 位，怎么知道路径能过多大的包？靠 **PMTUD（路径 MTU 发现）**：先按本机 MTU 发，路径中间上限更小的设备回一条 **ICMP 差错报文**（IPv4 类型 3 代码 4，"需要分片但设了不分片"），发送方据此调小一次再试，直到不再收到通知，此时尺寸就是整条路径能过的上限。

机制很优雅，问题出在前提上：**那条 ICMP 必须真的能回来。** 出于"安全策略"或历史原因，不少网络把 ICMP 整体屏掉，或只放行 echo（你能 ping 通）而拦掉差错报文。于是形成经典 **PMTU 黑洞**：

- 发送方设了 DF、按 1500 发；
- 中间设备想报错，通知被拦在半路；
- 发送方收不到反馈，继续按 1500 发；
- 大包一路被静默丢弃，用户端只有一个感受：**卡**。

| 能过 | 过不去 |
|:---|:---|
| ping（几十字节小包） | 满尺寸数据包 |
| DNS 查询 | 网页里的图片、字体、脚本 |
| TCP 三次握手（SYN 很小） | 握手之后的第一个满包 |
| 小文本页面 | 视频流、大文件下载 |

这就解释了最让人困惑的那类现象：**能 ping 通、能解析域名、首页能开，但内容加载不出来**。很多人在这里转去查 DNS、换浏览器、重装客户端，方向从一开始就错了。

IPv6 下更彻底：不允许中间分片，只能在源头发起，且 ICMPv6 承担的必要功能更多，被拦的后果更严重。IPv6 还规定了 **1280 字节的最小 MTU**，低于该值的链路被认为不合法。

## 五、隧道封装吃掉的那几十字节（最容易忽略的一节）

任何形式的隧道（VPN、代理的 TUN 模式、加密隧道）本质都是**把你原来的包整个装进一个新包里发出去**。新包多出来的外层头，占走的正是内层能用的空间。

| 封装方式 | 额外开销 | 内层有效 MTU 参考值 |
|:---|:---:|:---:|
| GRE / IP-in-IP | 24 / 20 字节 | 约 1476 / 1480 |
| IPsec ESP | 50 ～ 73 字节 | 约 1427 ～ 1450 |
| WireGuard | 约 60 字节 | 约 1420（IPv6 外层更低） |
| OpenVPN（UDP） | 约 69 字节 | 约 1410 |
| 运营商 IPv6 外层再套一层 | 再加 20 字节 | 1200 ～ 1400 区间 |

厂商出于保守，通常直接把隧道内的 MTU 设成 **1420、1400 甚至 1280**，宁可略微损失效率，也不让包超标。这也解释了客户端 TUN 配置里那个 `mtu` 字段——它不是摆设。

两个典型的隧道坑：

**坑一：外层变小了，内层不知道。** 内层还按 1500 发，进隧道就得分片，效率下降、丢一个碎片重传一整包。表现是"能连上但一传大文件就废"。

**坑二：两端不一致，变成单向故障。** 一端按 1420 发，另一端只认 1280，就会出现"我能发出去、对面收不到"或者反过来。排查极具迷惑性——链路是通的，只是单向的大包过不去。

最省事的处理不是死记数值，而是**让设备自己适配**：在隧道入口做 **MSS Clamping（MSS 钳制）**，拦截经过的 TCP 握手包，把里面带的 MSS 值改成"路径 MTU − 40"，两边 TCP 自动按更小的尺寸协商。它只影响 TCP 握手、不改全局 MTU，副作用最小。

```
# OpenWrt / 软路由上的常见写法（示意，接口名按自己环境调整）
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --clamp-mss-to-pmtu
```

注意：**MSS 钳制只对 TCP 有效**。走 UDP 的业务（QUIC、游戏、语音通话）本来就没有 MSS 可钳，只能靠调小接口 MTU 或依赖应用自行探测。所以如果你发现"网页都好了，但游戏或语音还是能连上却卡"，那多半是 UDP 这一侧还没解决。

## 六、怎么自己测：三条命令

**第一步，看本机接口 MTU 现在是多少。**

```bash
# Linux / macOS
ip link show                      # 看 mtu 字段
# Windows（管理员权限命令行）
netsh interface ipv4 show subinterfaces
```

**第二步，探测路径真正能过多少字节。** ICMP 头 8 字节 + IP 头 20 字节 = 28 字节固定开销，所以用 1500 − 28 = **1472** 作载荷起点，逐级往下试。

```bash
ping -M do -s 1472 目标地址     # Linux：-M do 不许分片
ping -f -l 1472 目标地址        # Windows：-f 不许分片
```

提示"需要分片但设置了不分片"，就把数字往下调 8 的倍数（1472 → 1464 → 1456 …）直到能通。**能通的最大值 + 28 = 这条路径的 MTU**。一路试到 1400 以下才通，说明路径上确实有瓶颈，或者你正处在一层隧道里。

**第三步，开隧道与不开隧道各测一次。** 这个对照最有价值：不算隧道能过 1472，开了只能过 1392，差值 80 字节就是封装开销的实测值，不是猜测。

补充两个观察手段：抓包过滤 `icmp` 看有没有类型 3 代码 4 的差错报文（有，说明通知没被拦，还有救；一条都没有，怀疑黑洞）；出现 `fragmented ip protocol` 说明正在分片，效率已经在掉。

**时间点也有讲究。** 路径 MTU 不是常量——负载均衡、多路径调度、不同时段的路由变化都会让实际路径不一样。白天没事、晚上有事，完全成立。有症状的时候测才有意义。

## 七、怎么改：从光猫到客户端，分五层

**1. 光猫 / 路由器 WAN 口（PPPoE 环境）**：MTU 设 **1492**，部分老线路 1480 更稳，可以试。这是最常见的一处默认错误。

**2. Windows**：

```cmd
netsh interface ipv4 set subinterface "以太网" mtu=1472 store=persistent
```

**3. Linux**：

```bash
sudo ip link set dev eth0 mtu 1492          # 临时生效，重启丢失
# 持久化：NetworkManager 的 ethernet.mtu，或 systemd-networkd 的 .network 文件
```

**4. 软路由 / OpenWrt**：优先用上面那条 **MSS 钳制**规则，而不是把全局 MTU 改小。全局改小影响所有流量且对 UDP 无效；钳制只针对 TCP 握手，方向更准、副作用更小。

**5. 客户端 / TUN 模式**：隧道配置里的 `mtu` 字段按实测值填；没有实测数据时，**1400 是个稳妥起点**（多数封装开销都能覆盖），别沿袭默认的 1500。

**改之前先记录原值**，改完复测，不行就回滚。改了一堆参数又忘掉原来是什么，只会让问题更难查。

## 八、这几个时候别动它

MTU 被过度调整的情况，比没调的多。

- **纯局域网、没有隧道、没有 PPPoE**：老实保持 1500。改小只会让同样数据拆成更多包，头部开销占比上升。
- **没有任何症状，只是"听说改了更快"**：别改。1400 相对 1500 大约多出 5% 的头部开销，这是净损失。
- **没有实测数据就填一个数字**：那是在赌。上面三条命令两分钟能跑完。
- **同时改好几处**：一次只动一个变量，改完复测。

这个参数的价值不在于"调得多好"，而在于**知道它存在**。真遇上"能连上但用不了"的故障，能想到查它，就已经省掉半天时间。

## 九、常见问题

**Q：我家是千兆宽带，为什么网页都打不开？** 千兆说的是带宽（每秒能搬多少数据），MTU 说的是单个包最多多长，两者完全独立。带宽决定快慢，MTU 决定通不通。

**Q：能 ping 通，是不是就说明网络没问题？** 恰恰相反。ping 默认只发几十字节的小包，天然绕开尺寸上限，这也是"能 ping 通但网页打不开"成为经典症状的原因。

**Q：把 MTU 改成 1400 是不是更稳定？** 只在有隧道、或有明确大包症状时才是。正确顺序永远是先测出实际路径 MTU 再决定。

**Q：为什么只有某几个网站打不开？** 不同目标走的路由不同，路径上的尺寸上限也不同。经过某段特定链路的站会受影响，走别的路的完全无感——所以换 Wi-Fi 或用手机热点，"坏掉的网站"常常突然就好了。

**Q：游戏和语音通话也会受影响吗？** 会，但处理方式不同。它们走 UDP，MSS 钳制管不到，得调接口 MTU。典型症状是能连上、能进房间，一开打就卡或掉线。

**Q：手机、热点需要手动改吗？** 基本不用，运营商侧和手机系统已经处理得比较好。手机这一侧真正值得检查的是客户端里的隧道 MTU。

**Q：换了另一条线路就恢复正常，能说明是 MTU 吗？** 能说明是路径问题。不同线路路径不同、尺寸上限也不同，原来那条路上的瓶颈没有了，症状自然消失。

**Q：用 tracert / mtr 能直接看出 MTU 吗？** 不能直接看。它们显示路径和每跳延迟，帮你判断有没有绕路；MTU 只能靠带"不许分片"标志的 ping 逐级试探。两者结合：tracert 看走哪儿，ping 探测看能过多大。

## 十、选线路时，这一项值不值得算

自己动手的能力有了，但并不是每个人都有空跟参数较劲。对绝大多数用户来说，MTU 这类问题应该由服务端和线路解决好——隧道封装方式、`mtu` 默认值、有没有做 MSS 钳制，都是服务商该处理的基础工作。用户要做的是**遇到"能连上但用不了"时能想到这个方向**，然后看一眼客户端的隧道设置对不对。

真要在源头少踩坑，选线路时看两件事：**是否明确说明隧道内的 MTU 处理方式**，以及**换线路之后症状会不会变化**（会变化说明路径质量有差异）。

## 十一、三句话总结

**第一，MTU 决定通不通，带宽决定快慢。** 测速数字漂亮和体验好用是两件事。

**第二，小包能过、大包消失，就先怀疑 MTU。** 尤其是"能 ping 通但网页打不开"这类症状。

**第三，有隧道就一定算上封装开销。** 那几十个字节不是可以忽略的零头，它决定了你的大文件能不能传完。
