# 带宽跑不满别急着换线路：带宽时延积、TCP 拥塞控制与缓冲膨胀讲透

> 原文：https://huanghaiwan.com/posts/tcp-congestion-bandwidth-guide-2026/

有一条监控曲线值得记住：某业务的晚高峰，带宽只用了 40%，用户却在成批超时。抓包一看，TCP 往返时间涨到 200ms 以上，发送窗口被拥塞控制算法自己砍小了——路没堵，是开车的人不敢踩油门。这种情形不只是机房里的故事，你家那条 100Mbps 的线路下载海外文件只跑出 10Mbps，也常常是同一类账没算清。

**一句话结论：跨境链路的瓶颈经常在协议栈这一端，而不是带宽本身——带宽时延积决定单条连接能跑多快，丢包按平方根级别砍吞吐，缓冲膨胀吃掉交互体验；终端能优化的部分做完之后，剩下的才是该换线路的部分。**

## 太长不看

| 问题 | 短答 |
|:---|:---|
| 100Mbps 下载只有 11MB/s，正常吗 | 正常。比特除以 8，12.5MB/s 是理论上限，扣掉协议开销 11MB/s 上下即满速 |
| 单条连接跑不到标称速度 | 多半是带宽时延积：100Mbps × 200ms 需要约 2.5MB 在途数据，窗口不够只能干等 |
| 跨境丢包 1% 有多致命 | 经典模型下 100ms 往返 + 1% 丢包，单连接上限压到 1.4Mbps 量级；丢包降到四分之一，吞吐才翻倍 |
| BBR 有用吗 | 用带宽时延积建模代替「丢包即拥塞」，跨境长肥管道有收益，但它是效率算法不是加速器 |
| 测速满格但开网页卡 | 缓冲膨胀。排队时延吃体验，跟平均吞吐量是两笔账 |
| 什么时候真该换线路 | 加连接数也上不去、晚高峰延迟翻 2-3 倍、路由绕第三国——命中就要换物理线路 |

## 一、先算三笔账

**单位账。** 服务商说 Mbps，下载工具显示 MB/s，中间差 8。100Mbps 折 12.5MB/s，扣掉每包 2%–5% 的协议开销、再加 PPPoE 拨号多占的 8 字节，稳定跑在 11MB/s 到 12MB/s 就算发挥正常。九成「感觉被骗」都死在这一步换算上。

**口径账。** 设备上的「限速 100Mbps」是时间平均限速，不是每毫秒都掐死。按 1500 字节的标准包算，理论节拍是每 120 微秒放一个包——这个尺度比一次系统调用还短，操作系统和网卡做不到分毫不差，所以短窗口测出来的速率必然上下跳。验证带宽请用秒级窗口或多次采样平均值，别盯着瞬时波峰下结论。

**连接数账。** 同一个服务器，浏览器单线程 3MB/s、十六线程下载器 11MB/s，不是下载器有黑科技，是单条 TCP 连接本来就填不满管道。为什么填不满，见下一节。

## 二、带宽时延积：管道再宽也填不满

带宽时延积（BDP）= 带宽 × 往返时延，算的是「要跑满这条管道，得有多少数据同时在路上」：

```
100 Mbps × 0.2 s = 20 Mbit = 2.5 MB
```

也就是说，往返 200ms 的线路上，你得在收到确认之前先塞进去 2.5MB，才能真正跑满 100Mbps。而能同时在途多少数据，由滑动窗口决定。窗口给 64KB 时：

```
64 KB ÷ 0.2 s = 320 KB/s ≈ 2.6 Mbps
```

**买的是 100Mbps，跑出来 2.6Mbps，锅在窗口。** 这不是编出来的极端案例，早期跨境访问的观感就是这么来的。

后来 TCP 加了窗口缩放（RFC 1323，后由 RFC 7323 更新），操作系统也能自动调整接收缓冲区，硬瓶颈缓和了很多。但两个因素还在拽后腿：一是**拥塞窗口的增长需要时间**，从初始的 10 个报文涨到能填满 2.5MB 在途数据要几十个往返，任务越短、时延越长，有效带宽越低；二是**丢包会把窗口打回去**。

跨境链路把这些问题放大，根子在距离上。访问北美西海岸理论最低往返 150ms 上下，到欧洲 200ms 往上，这是光速和海缆定的。距离越长，同样的窗口相对带宽越不够用——业内管这种高带宽高时延的链路叫「长肥管道」。

## 三、丢包为什么是断崖：三代拥塞控制算法

TCP 有一套自我约束机制，它的演进史正好解释了跨境链路上的很多怪现象。

**第一代（Reno 时代）把丢包等同于拥塞。** 连接起步走慢启动，指数增长试探上限；接近上限转线性增长；一旦丢包，窗口立刻砍半再慢慢爬。因为经典模型假设丢包只有一个原因——某处队列满了，所以算法把丢包当「前面堵了，快退」的信号。按经典估算式（吞吐量 ≈ MSS ÷ (往返时延 × √丢包率)）可以估个量级：

| 场景 | 单连接吞吐量级（估算） |
|:---|:---|
| 往返 20ms、无丢包 | 不受丢包限制，能否跑满看窗口和带宽 |
| 往返 100ms、丢包 1% | 约 1.4 Mbps |
| 往返 200ms、丢包 1% | 约 0.7 Mbps |
| 往返 200ms、丢包 0.25% | 约 1.4 Mbps |

关键结论：**吞吐量大致与丢包率的平方根成反比。** 丢包降到四分之一，吞吐才翻一倍——这就是为什么把丢包从 2% 优化到 1% 无感，从 1% 压到 0.1% 却像换了条线路。表里是偏保守的老模型估算，Linux 默认的 CUBIC 和 BBR 实际好上数倍，但断崖级别这个规律不变。

**第二代 CUBIC** 换掉线性增长曲线，用三次函数描述窗口变化，恢复更利索，成了很长时间里 Linux 的默认。但它依然是**基于丢包的损失模型**。问题在于跨境链路上的丢包未必来自拥塞：国际出口抖动、中间设备随机丢弃、无线干扰都会丢包，CUBIC 分不清这两类，统统当堵车处理，窗口被反复砍小——前面「带宽只用了 40% 却成批超时」的案例就是这个机制的后果。

**第三代 BBR** 的做法更干脆：不把丢包当拥塞信号，转而持续测量**瓶颈链路带宽**与**最小往返时延**，据此算出管道里该有多少在途数据，主动把发送速率维持在这个水平上。往返 200ms、随机丢包 0.5% 的线路上，CUBIC 会一路降速，BBR 倾向于忽略这类非拥塞丢包继续发送。跨网、跨运营商、长距离场景开 BBR（内核参数 `net.ipv4.tcp_congestion_control=bbr` 配合 `fq` 队列）通常能拉起不少效率，这也是 IDC 排查「带宽跑不满」时的常规动作。

边界要说清楚：BBR 只提升单连接对带宽的利用效率，不创造带宽、不降低物理时延；它和 CUBIC 共存时有公平性争议（往往抢到更多份额）；现在还有 BBRv2、BBRv3 等后续版本在迭代，2026 年仍能看到 BBRv3、SCReAM、GCC v2 这类实时传输算法的实测对比。协议成熟不等于实现成熟，选服务商时可以留意客户端与内核的维护活跃度。另外它跑在链路两端，你能开的只有本地设备和服务商那一侧。

## 四、缓冲膨胀：带宽用了 40%，体验照样烂

这一节的问题不是填不满管道，而是**管道用满了路却走不动**。路由器里的缓冲区本意是好的：短暂拥塞时先排队，别急着丢包。麻烦出在排队长度上，算法简单得让人心慌：

```
排队时延 = 缓冲区大小 ÷ 带宽
```

1MB 缓冲区放在 10Mbps 上行链路上，就能制造 0.8 秒排队时延——视频会议里这就是「画面还在，声音像在水里说话」。这种现象叫**缓冲膨胀**，症状非常迷惑人：测速跑满格、下载大文件正常，可一开网页就转圈、视频会议音画错位、有人上传文件时全家网络一起卡。原因在于测速软件测的是吞吐量，体验吃的是时延；缓冲区里堆着几百毫秒的数据，吞吐照样好看，交互已经废了。

有个反直觉的实测结论印证这件事：把公网链路带宽从 10M 加到 100M，大文件整体传输时间并没有下降多少——带宽变宽后中间设备能存下更多数据，排队时延反而抬头，高带宽链路在拥塞恢复阶段有时还不如低带宽链路。家庭场景的解法是**智能队列管理**：路由器上的 SQM（配 CAKE 或 fq_codel）把缓冲队列管短，限速填成实际带宽的 85%–90%，留点余量给算法腾挪，填满标称值反而会让它失效。

## 五、终端侧能做的 7 件事

按「见效快、门槛低」排序：

1. **多连接。** 下载器支持多线程就开（`aria2` 常用 `-x16 -s16`）；服务器端限单 IP 并发时无效。
2. **优先有线。** Wi-Fi 在干扰环境下丢包率轻松上到百分之几，对 TCP 是灾难性的。
3. **路由器开 SQM。** 家里有人上传、打游戏、开视频会议时收益最明显。
4. **排查 MTU / MSS。** PPPoE 下 MTU 通常 1492、对应 MSS 1452；设置不对会「能 ping 通但网页打不开」。用 `ping -M do -s 1472` 逐级往下试。
5. **认清上行瓶颈。** 家用宽带上行常只有下行十分之一，上传素材、推流、云备份吃的是上行。
6. **把测速方法做对。** 选同城或同运营商骨干节点，秒级窗口看平均值，单线程与多线程各测一次；服务器侧用 `iperf3` 本机测，先确认网卡本身能跑多少。
7. **别在晚高峰赌单线程大流量。** 晚七点到十一点国际出口最紧张，几十 GB 的单线程传输放到白天或后半夜，成功率明显不同。

## 六、什么时候问题真的在线路上

三条判据，命中就是物理线路和路由的事，终端怎么调都没用：

1. **同一线路，多连接也上不去**——单连接慢可能是窗口，多连接还慢就是链路真挤；
2. **晚高峰往返时延翻 2-3 倍且丢包上升**——国际出口供需错配的典型特征；
3. **路由绕了第三国**——数据包本该直飞却先绕别处，多出来的每一跳都是延迟。

回到公式就明白：往返时延是分母。**把 RTT 从 200ms 压到 60ms，单连接吞吐上限直接变成三倍多。** 所以线路类型的差异最终都兑现成两件事——更短的往返、更低的丢包。普通中转线路先接入口节点再出境，路径多一跳；IEPL / IPLC 这类专线走点对点链路，独享带宽、不过公网出口，晚高峰的抖动和丢包明显更可控。这也是为什么同样的带宽数字，专线跑出来的实际吞吐经常高一截。两类线路的差别与真假专线分辨，见 [跨境线路类型怎么选](https://huanghaiwan.com/posts/network-line-type-guide-2026/)。

协议层还有一层补充：服务商在链路上做多路径传输（MPTCP）时，会把一条逻辑连接拆成多条子流走不同路径，某条路径拥塞或断掉时流量自动调度到健康路径。它的价值是**保险**而不是加速，能让你在晚高峰不至于从 20Mbps 掉到 2Mbps，原理与真伪分辨见 [MPTCP 多路径传输讲清楚](https://huanghaiwan.com/posts/mptcp-multipath-guide-2026/)。

## 七、常见问题

**单连接和多连接该看哪个数字？** 看你要干什么。看视频、开网页是多连接场景；大文件下载、Git 克隆、单线程传素材是单连接场景，往往差一大截。验收时两个都测。

**路由器怎么开 BBR？** 取决于固件内核。OpenWrt 系一般可装 `kmod-tcp-bbr` 并设置 `net.ipv4.tcp_congestion_control=bbr`，队列算法配合 `fq` 或 `cake`；原厂固件大多不开放，这也是很多人换软路由的原因。开完用 `sysctl net.ipv4.tcp_congestion_control` 确认。

**开了 SQM 测速变低了，是不是白开？** 测速数字会降，因为它是用限制队列长度换时延。人多、有上传、有游戏时体验明显变好；单人单机下载收益有限。

**专线一定更快吗？** 不一定跑分更高，但晚高峰更稳。专线买的是独享带宽和不走公网出口的路径质量，白天看不出，晚上八点差别就出来了。

**怎么判断丢包是拥塞丢包还是随机丢包？** 看时间分布：只在晚高峰出现、伴随延迟飙升的多半是拥塞；全天均匀的零星丢包更可能是链路质量或无线干扰。前者换更优线路有用，后者先排查本地 Wi-Fi 和路由器。

**这些优化能让我白嫖更高速度吗？** 不能凭空变出带宽。收益都来自「把买到但没用上的容量用尽」和「让体验少受时延拖累」。全做完还是那个速度，那就是真实上限。
