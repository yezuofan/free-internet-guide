# MCP 协议完全指南 2026 下半年：规范改成无状态核心之后，普通用户和开发者分别怎么用

> 原文：https://huanghaiwan.com/ai/mcp-protocol-guide-2026/

先摆一个数字。Algolia 复盘 2026 年企业 Agent 落地情况时给出的统计是：真正推到生产环境的 Agent 失败率在 70% 到 95% 之间，而其中约六成失败跟模型强弱没关系——问题出在数据质量、上下文缺口和权限治理这三件事上。想让 AI 从「会聊天」变成「会干活」，卡点从来不是再换一个更强的模型，而是模型外面那层「接口怎么接、数据谁管、权限谁批」。

MCP（Model Context Protocol，模型上下文协议）解决的就是这层。给它一个更直白的定义：AI 世界的 USB-C 接口——一次实现，所有支持的客户端都能插上就用。

但要提醒一句，这份协议的底座在 2026 年 7 月 28 日动了一次大手术：第 5 版规范把「有状态连接」整体换成「无状态核心」。网上大量 2025 年写的配置教程，正好横跨在这次断层两侧。

**一句话结论：MCP 从 2026-07-28 规范起变成无状态协议，握手、会话 ID、服务端主动请求都被删掉了，每个请求自带上下文、可以打给任意实例。开发者省掉粘性会话和共享存储，普通用户要留意的是——照半年前的教程配客户端，很可能配不上。**

## 一、它到底解决了什么问题

在 MCP 之前，每个 AI 工具连外部数据都是各写各的：Claude 一套插件、ChatGPT 另一套、VS Code 插件再一套。三个 AI 连同一个文件系统，要维护三份适配代码——这是典型的 N×M 问题。

MCP 把中间那层抽出来：任何 AI 客户端 → 同一个 MCP 服务器 → 文件系统。工具提供方只实现一次，所有支持的客户端复用。

三个角色要分清，不然看文档会绕晕：

- **Host（宿主）**：你在用的 AI 客户端本身，Claude Desktop、Cursor、VS Code、Codex CLI 都算。
- **Client（客户端）**：宿主内部负责连服务器的组件，负责协议协商与请求收发。
- **Server（服务器）**：真正干活的进程，暴露三类能力——Tools（工具，模型主动调用）、Resources（资源，可读的数据与文档）、Prompts（提示词模板）。

对三类人的价值不一样：普通用户是「配一次、换工具不用重学」；开发者是「写一个服务器，所有 AI 应用都能用，不用给每家模型写适配层」；企业是「一个网关统一管权限、审计和限流」。

## 二、2026 年 7 月那次修订，改了什么

第 5 版规范（版本号 2026-07-28，前一版是 2025-11-25）被官方定性为「自协议问世以来最重要的一次修订」。核心只有一句：协议状态从有状态改成完全无状态。

| 维度 | 旧（2025-11-25 及以前） | 新（2026-07-28） |
|:---|:---|:---|
| 连接模型 | 长连接 + 会话，类似 TCP | 每个请求自包含，无会话 |
| 初始化 | 必须先 `initialize` 握手 | 取消协议级握手 |
| 会话标识 | 服务端下发 `Mcp-Session-Id`，后续请求必须回传 | 删除会话 ID |
| HTTP 传输 | 同一端点支持 POST 与 GET，支持 SSE 可恢复流 | 只允许 POST，无 GET 流、无可恢复流 |
| 请求上下文 | 依赖会话状态 | 每个请求通过 `_meta` 自描述 |
| 部署形态 | 多实例要粘性会话或共享会话存储 | 可无状态部署，适配 Lambda、Workers 这类无服务器环境 |
| 服务端主动请求 | 采样、elicitation、roots 直接发起 | 改为带内 `input_required` 重试模式（MRTR） |
| 扩展机制 | 核心规范自带 | 版本化扩展框架，MCP Apps、Tasks 转为扩展 |

驱动这次改动的主因是水平扩展。旧形态下，会话常常绑在某一个实例上，负载均衡被迫做 sticky，多副本部署还要维护共享会话存储——一个连了几十个工具的 Agent，会话状态散在哪儿就是运维的噩梦。改成无状态后，请求可以路由到任意网关或任意实例。

对普通用户来说，这次改动大多是透明的：客户端和官方服务器会各自动升级。真正的坑在于版本断层——老客户端连新服务器（或反过来）会出现「连上了但工具列表是空的」这类怪现象，对应开发者要做的，是让服务端留好 2025 时代的兼容层。

## 三、三种用法：从零代码到写代码

### 方式一：Claude Desktop（不写代码那条路）

1. 装好 Claude Desktop，打开 **设置 → 开发者 → 编辑配置**；
2. 在配置 JSON 里加一个文件系统服务器：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/你的用户名/Documents"]
    }
  }
}
```

3. 重启客户端，界面上会出现服务器指示器，点开能看到可用工具；
4. 然后你就能直接说「把 Documents 里的 PDF 按主题归一下类」——它真的去读文件、真的去改文件。

三个最容易踩的点：路径必须是绝对路径，`~` 不认；macOS 首次会弹权限申请，别点拒绝；`npx` 第一次拉包要几十秒到几分钟，别以为卡死了。

### 方式二：编辑器与 CLI 集成

VS Code 走的是 `.vscode/mcp.json`，字段名是 `servers`（不是宿主配置里的 `mcpServers`），支持 `"type": "local"` 与远程 URL 两种；命令面板里搜 `MCP: Open User Configuration` 可以直接打开用户级配置。Cursor、Trae、Codex CLI 的写法大同小异，都是「一个 JSON 文件 + 一条启动命令」。

### 方式三：SDK（自己写服务器）

官方 SDK 覆盖 Python、TypeScript、C#、Go、Java、Rust 等语言。**这里是最新的坑：Python SDK 已经发布 v2，属于「SDK 重建 + 协议升级」双线并行**——底层换成客户端与服务端共享的调度引擎，高层 API 大面积重命名（最典型的是 `FastMCP` 变成 `MCPServer`），同时新增一等公民 `Client` 对象；协议侧实现 2026-07-28 修订版，并通过兼容层继续服务旧客户端。

所以从 2025 年的文章里抄 Python 代码，第一行 import 就可能报错。升级路线本身不复杂，难的是先意识到「v2 是一次重构，不是打补丁」。

对企业用户，2026 年下半年还多了一条省事的路子：**Google Cloud 在 9 月 24 日给 API Gateway 加了原生 MCP 支持**——已经在 OpenAPI 3.x 描述里部署好的 REST 接口，加一段 MCP 注解就能让网关本身充当远程 MCP 服务器。过去给 Agent 暴露内部接口，标准做法是再写一层 MCP 中间层，鉴权、限流、日志、错误处理全要复制一遍，同一条业务能力从此有两套入口；现在这层维护成本可以砍掉。

国内生态也在长：企查查的智能体数据平台 2026 年 3 月底上线，走「MCP × CLI」双轨接入，对外开了近 200 项原子能力，已进阿里云百炼、扣子、飞书等平台。对做企业数据查询的人来说，这类「官方数据源 + 现成 MCP 服务器」比自己爬要省太多事。

## 五、MCP 和 A2A 不是对手

2025 年 4 月 Google 发布 A2A（Agent2Agent）之后，问「哪个会赢」的人一直不少。答案是两者不在同一层，也不需要二选一。

| 维度 | MCP | A2A |
|:---|:---|:---|
| 解决什么 | Agent 连接工具与数据 | Agent 之间互相通信 |
| 比喻 | USB-C（标准化接设备） | TCP/IP（标准化通信） |
| 模式 | 客户端-服务器 | 点对点 |
| 治理 | Linux 基金会 AAIF | Linux 基金会 |

典型组合是企业客服系统：MCP 负责把 CRM、邮件系统、知识库接进 AI；A2A 负责把复杂订单问题从「客服 Agent」转给「订单处理 Agent」，结果再传回来。A2A 1.0 之后的一个硬要求是 Agent 必须声明能力契约——从「你能做什么」变成「你承诺做什么」，这对多 Agent 协作的可靠性是实打实的改进。

## 六、2026 年真正该盯的是安全，不是功能

9 月 7 日，安全公司 Adversa AI 发布了一份 MCP 安全汇总报告，在受审计的 MCP 服务器里累计数出 68 个可报告漏洞，并关联了一个代号 Deadbugz 的攻击活动；9 月 11 日 AI Governance Institute 跟进，用的词是「系统性缺口」。系统在哪：同一组数据里，**受审服务器中有 91.8% 没有接 OAuth 认证**。

十台设备九台没装门锁，出现 68 个洞就不奇怪了。

对企业来说，单点工具化解决不了这个问题，得在架构上做：Agent 要有独立身份而不是共用人类账号；工具调用要经过统一网关做策略、审计和限流；高危操作（改数据、发消息、动钱）默认走人工确认。

Google 9 月中旬开放 Google Home 给通用 Agent 的做法，可以当作权限边界的参考样本：任何支持 MCP 的 Agent 都能读设备状态、查事件、开关灯光、调温控，但门槛写得很直白——仅限美国、需要 Google Cloud 与 OAuth、要 Home Premium Advanced 订阅，开锁这类高危动作默认禁用。能用什么、不能碰什么，写死在协议层，而不是靠提示词提醒模型「请谨慎」。

## 七、国内用起来顺不顺，还是看链路

MCP 本地服务器（Filesystem、Git、Memory、Playwright）离线也能跑，这部分不受影响。会掉链子的是三类场景：登录 Claude Desktop 或 Cursor 这类海外客户端、调远程 MCP 端点、让 Agent 长时间拉仓库装依赖下模型。

按「长期跑 MCP 工具链」这个场景排，重点是三条：连接要能扛住长时间占用、出口身份要固定（否则远程服务器那边的 OAuth 会话会因为 IP 跳区反复失效）、流量要够（一次任务里工具调用可能几十上百次）。

## 八、常见问题

**MCP 和 Function Calling 是不是一回事？** 不是。Function Calling 解决的是「模型怎么输出一次工具调用」，各平台格式还各写各的；MCP 解决的是「工具怎么被标准化接入、一次实现到处复用」。前者在模型侧，后者在生态侧。

**只有 Claude 能用吗？** 早就不是了。ChatGPT、VS Code Copilot、Cursor、Trae、Codex CLI 等都已支持，OpenAI 也已经进了 AAIF 参与联合治理。

**配置 MCP 要会编程吗？** 普通用户不用，复制 JSON 即可；要自己写服务器才需要 SDK。

**2026 年 7 月改无状态之后，我原来的配置会不会失效？** 本地服务器基本不受影响，受影响的主要是远程服务器与自研服务端的部署方式；遇到「连上但没有工具」的情况，先核对客户端与服务端各支持哪个规范版本。

**MCP 安全吗？** 协议本身提供了路径白名单、OAuth 2.0 等机制，但生态现状不好看——九成以上的服务器没接认证。原则是：只装自己看得懂、来源清楚的服务器，给 Agent 的权限按最小必要给，高危操作保留人工确认。

**哪里找更多服务器？** 官方 Registry 预览版、GitHub 上的 modelcontextprotocol/servers，以及 npm / PyPI 上搜 `mcp-server` 关键字。
