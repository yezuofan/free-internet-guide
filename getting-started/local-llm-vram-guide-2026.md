# 本地部署大模型要多少显存？量化档位与引擎选择一次说清

有人贴出一张 16GB 显卡的购物车问我能不能跑 27B，我回他：能跑，但你大概率跑完第一次就想关掉。

这两年被问得最多的就是这句「我这台机器能不能本地部署」。答案之所以总是模棱两可，是因为大部分人拿「能不能加载」当标准。加载进去只是起跑线，跑起来之后每秒吐几个字、能不能开长上下文、会不会一开浏览器就爆显存，才是决定你留不留它的问题。

先把话说清楚：下面的体积全部按公式算出来，你可以拿计算器复核；速度是带宽除体积推的**理论上限**，不是我在某台机器上跑的分。三笔显存账缺一笔就会 OOM。

## 三笔账，只算一笔必爆

**权重。** 参数量（B）× 每权重比特数 ÷ 8 = GB。30B 的模型按 4.5 bit 存，就是 30 × 4.5 ÷ 8 ≈ 16.9GB，FP16 则要 60GB。

**KV 缓存。** 跟参数量无关，跟层数、KV 头数、上下文长度正相关。32 层、8 个 KV 头、每头 128 维、FP16：8K 上下文约 1.07GB，32K 约 4.3GB，128K 约 17.2GB。上下文翻 16 倍，这笔账也翻 16 倍。

**运行时与碎片。** CUDA 上下文、驱动、分配器，留 1.5GB 到 3GB；Windows 还要给桌面合成器让路。三笔加起来再乘 1.15 的保险系数，才是真实门槛。

## 量化档位：省的是显存，赔的是能力

| 档位 | 每权重比特 | 30B 体积 | 判断 |
|:--|--:|--:|:--|
| Q2_K | 2.6 | 9.8GB | 能读字，专业问题开始编 |
| Q3_K_M | 3.9 | 14.6GB | 应急可用，逻辑题掉得明显 |
| Q4_K_M | 4.5 | 16.9GB | 甜点，掉点可接受 |
| Q5_K_M | 5.7 | 21.4GB | 显存有余时的首选 |
| Q6_K | 6.6 | 24.8GB | 收益已经很小 |
| Q8_0 | 8.5 | 31.9GB | 接近无损，图安心 |
| FP16 | 16 | 60GB | 家用没必要 |

排序规则只有一条：**先降参数，再降量化**。宁可跑 14B 的 Q4_K_M，也别跑 32B 的 Q2_K——后者省下的 7GB 会以「答非所问」的形式还给你。

## 五个引擎怎么分工

| 引擎 | 默认端口 | 上手 | 量化可控 | 适合谁 |
|:--|:--|:--|:--|:--|
| Ollama | 11434 | 一行命令 | 中 | 想立刻用上模型 |
| LM Studio | 1234 | 图形界面 | 高 | 不写代码 |
| llama.cpp | 自定 | 参数全手填 | 最高 | 要抠 `-ngl`、`-c` |
| vLLM | 8000 | 要 Linux + CUDA | 中 | 做服务、要并发 |
| MLX | 自定 | 只认 Apple Silicon | 中 | Mac 榨统一内存 |

Ollama 和 LM Studio 开箱就带 `/v1/chat/completions`，把 SDK 的 base_url 改掉就能顶替云端接口。llama.cpp 也有兼容服务 `llama-server`，只是每个参数都得自己写清楚。

## 按显存档位选模型（4~5bit、8K 上下文、单人用）

| 显存 | 典型卡 | 舒服跑 | 建议 |
|:--|:--|:--|:--|
| 8GB | 4060 / 3070 | 7B 到 9B 的 Q4_K_M | 脚本、翻译、摘要 |
| 12GB | 4070 / 3060 12G | 14B 的 Q4_K_M | 日常问答性价比区间 |
| 16GB | 5060 Ti / 4060 Ti 16G | 14B 的 Q5_K_M，或 27B 的 Q3 | 想尝 27B 就别嫌慢 |
| 24GB | 3090 / 4090 | 27B 到 30B 的 Q4_K_M | 甜点，建议停在这 |
| 48GB | 双卡 / RTX 6000 Ada | 70B 的 Q4_K_M | 该算电费了 |
| 64GB+ | 多卡或服务器 | 百亿激活的 MoE | 不是家用场景 |

两个例外必须点出来。Mac 的统一内存是另一套算法：M4 Max 给到 128GB 内存能装下更大的权重，但带宽只有 400GB/s 出头，装得下不等于跑得快。多卡也不是线性叠加，两张 16GB 拼 32GB，模型照样得切分，层间同步有开销。

## MoE 打破了算力，没打破显存

Kimi K3.1 Pro 沿用 K3 的混合专家设计：总参数 2.8 万亿、896 个专家、每次只激活 16 个、等效激活约 1040 亿。按媒体报道，FP16 要约 5.6TB 显存，INT4 也得约 1.4TB，80GB 的卡跑 INT4 至少 18 张，权重计划 11 月 4 日前开放。

激活参数决定计算量，总参数决定显存。所以判断只有一句：**看总参数定显存，看激活参数估速度**。总参数过千亿的，直接放弃本地念头去调 API。同样道理，Qwen3.8 全系里给家用准备的是 27B 稠密版，那个 2.4T-A95B 的旗舰权重光 BF16 就要约 4.9TB；GLM-5.3 是 7430 亿参数。

## 速度：带宽除以体积，小学数学

解码阶段每吐一个 token 基本要把整套权重过一遍，所以理论上限 ≈ 带宽 ÷ 权重体积。

- RTX 4090：1008GB/s ÷ 17GB ≈ 59 token/s，实测打五六折，30 到 40 是常态
- RTX 4060：272GB/s ÷ 17GB ≈ 16 token/s，实际 8 到 12
- DDR5 双通道：约 100GB/s ÷ 17GB ≈ 5.9 token/s，这就是「CPU 也能跑」用起来像拨号上网的原因
- Mac M4 Max：400GB/s ÷ 17GB ≈ 23 token/s

这个公式能立刻打掉营销话术。有人报 30B 跑 200 token/s，你先看模型多大：3B 的 Q4 报这个数可信，30B 报这个数，要么是批处理摊薄了单个请求，要么数字压根没对上。

## 什么时候别本地跑

批量翻译、日志归类用本地 14B；写长文、复杂推理切回云端旗舰；涉密材料才必须本地断网，这是本地唯一不可替代的场合；高并发服务单卡撑不住 10 个并发，要么 vLLM 要么云。

## 15 分钟跑通

```bash
  # Ollama 官网 ollama.com 有各平台安装包
curl -fsSL https://ollama.com/install.sh | sh
  # qwen3.8 官方只发了 27B，8B 级别练手用 qwen3:8b
ollama pull qwen3:8b
ollama run qwen3:8b
  # 看它到底吃多少显存，别靠猜
ollama ps
```

想看细账就换 llama.cpp，从 `-ngl 20` 开始一层层加，`watch -n1 nvidia-smi` 挂旁边：

```bash
./llama-server -m ./qwen3.8-27b-q4_k_m.gguf -ngl 40 -c 8192 --port 8080
```

最实用的一条经验：**先把上下文定死，再调层数**。反过来调会一直在两种变量之间绕圈。

## 五个坑

1. 显存没满却 OOM：多半是碎片或上下文超了，开 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，或者把上下文砍一半再试。
2. GGUF 拉错档：`Q4_K_M` 和 `Q4_0` 体积接近、质量差一档，认准带 K 的混合量化。
3. 以为 CPU 卸载能救场：能跑起来，速度掉到个位数 token/s。
4. Mac 把内存算满：统一内存要和系统、浏览器、IDE 抢，64GB 的机器给模型留 48GB 才算稳。
5. 把带 `-cloud` 后缀的 tag 当本地跑：那是转到官方服务器，`ollama ps` 里只有 `100% GPU` 才是真本地。
