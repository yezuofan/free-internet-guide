# QUIC 和 HTTP/3 是什么？为什么跑 UDP 的网站有人更快、有人更卡（2026 科普）

> 本文最初发布于 [huanghaiwan.com](https://huanghaiwan.com/posts/quic-http3-guide-2026/)

QUIC 全称 Quick UDP Internet Connections，最初由谷歌在 2012 年牵头推进，后来被 IETF 收编为正式标准：RFC 9000 定义传输本身，RFC 9002 管丢包检测与拥塞控制，RFC 9001 规定加密走 TLS 1.3，HTTP/3 则是 RFC 9114（2022-06-06 发布）。

一句话概括它干的事：**把原先分散在三处的能力——TCP 的连接管理、TLS 的加密握手、HTTP/2 的流复用——揉到一起，塞进 UDP 这个壳子里重新实现一遍。**

## 一、TCP 的三个老毛病

TCP 是 1970 年代设计的东西，可靠有序、久经考验，但随着网络从窄带高误码变成移动网络加跨洲光纤，三个毛病越来越明显。

**建连太慢。** 一个普通 HTTPS 请求要 TCP 三次握手（1 个 RTT）、TLS 1.3 握手（再 1 个 RTT），然后才轮到发请求等响应，最少 3 个 RTT 起步。跨省骨干延迟按 30ms 算，光握手就吃掉 60ms，还没算 DNS 解析。手机端每次开 App、切 Wi-Fi 都可能触发重建连接。

**队头阻塞。** TCP 是一条有序字节流，底层只认一条队列。中间某个包丢了，接收端必须等这个洞补上，后面完好到达的数据也只能在缓冲区干等。HTTP/2 用多路复用解决了应用层排队，但 TCP 层的队头阻塞还在，而且一条连接承载更多并发请求等于放大了单点丢包的影响。好比单车道公路上一支车队，最前面一辆抛锚，后面全部停下等。

**连接迁移困难。** TCP 连接用"四元组"标识——源 IP、源端口、目的 IP、目的端口，任何一个变了连接就失效。手机从 Wi-Fi 切 5G、笔记本从家换到公司、进出地铁隧道拿到新 IP，连接直接断，应用层得重新握手。

## 二、QUIC 的三条主线

**1-RTT 建连 + 0-RTT 恢复。** QUIC 把 TLS 1.3 握手融进连接建立过程，不再串行。新建连接一次往返即可开始传数据；回访时客户端可以在第一个包里就带上业务数据（0-RTT），代价是有重放风险，标准要求服务端配置防重放窗口兜底。移动端弱网体感差别最明显。

**流级独立，真多路复用。** 数据拆成互相独立的 stream，各自编号、各自确认，丢包只影响所属那条流。HTTP/2 的多路复用是建立在 TCP 字节流之上的伪多路，QUIC 的多路复用是传输层自己就支持的。还是公路比喻：QUIC 修了多条平行车道，一条堵了其他照跑。

**连接迁移靠 Connection ID，不认 IP。** 换 Wi-Fi、换基站、换 IP，只要连接 ID 还在连接就不断，正在传的数据不重来。

另外 QUIC 强制使用 TLS 1.3，不允许明文、不允许降级。

## 三、别把 QUIC 和 IEPL、MPTCP 混成一回事

| | QUIC / HTTP/3 | MPTCP | IEPL |
|:---|:---|:---|:---|
| 层面 | 传输协议，网站服务端与浏览器之间用 | 传输协议，用于多路径调度 | 物理线路，独享带宽不经过公网 |
| 谁在用 | 网站、浏览器、CDN 厂商 | 客户端软件与加速服务商之间 | 加速服务商内部 |
| 解决什么 | 建连慢、队头阻塞、换网断连 | 单线拥塞或故障时没有后备 | 跟公网流量挤带宽 |
| 用户能控制吗 | 不能，网站那端说了算 | 能，看服务商实现 | 能，就是你在买的东西 |

一句话分清：**QUIC 是"网站那边的协议"，浏览器里看不见；MPTCP 是"多备胎调度"；IEPL 是"路本身"。** 三者层级不同，可以叠加，不是替代关系。

有些说法把它们揉成一团，暗示"买了哪家线路就能享受 QUIC 加速"。事实是：**网站走不走 QUIC 由网站自己的服务端决定，任何线路服务商都改不了这个选择。** 但线路能决定另一件事——当网站真的走了 QUIC 时，这条链路放不放 UDP 走。

## 四、为什么有的网站开了 HTTP/3 反而更卡

先记住前提：**QUIC 全程跑在 UDP 上。** 这个选择在部署上很聪明（几乎所有设备都支持转发 UDP），但埋了个雷——UDP 长期是"被区别对待"的协议。相对 TCP 而言，UDP 没有连接状态、识别和调度机制不成熟，在跨境链路上被限速、被丢弃并不罕见。

于是出现反直觉的结果：**同一个网站，走 TCP 的 HTTP/2 能用，走 UDP 的 HTTP/3 反而卡死、转圈、甚至打不开。**

更麻烦的是它不会报错。Chrome、Firefox、Safari 都默认尝试 HTTP/3，连不上就静默回退到 HTTP/2——不弹提示、不写日志。用户感受到的只有一句模糊判断："这个网站特别慢。"

自己验证的四个办法，由浅到深：

1. **开发者工具。** F12 打开 Network 面板，右键表头勾上 Protocol 列，刷新页面，看标的是 `h3`、`http/2` 还是 `http/1.1`。
2. **Chrome 专门入口。** 地址栏输入 `chrome://net-internals/#http3` 看 HTTP/3 连接状态；或去 `chrome://flags` 搜 QUIC 临时禁用做 A/B。
3. **命令行对比。** 用带 HTTP/3 支持的 curl 分别跑 `--http3-only` 和 `--http2`，看建连耗时。
4. **最省事的一招。** 同一站点、同一时段，分别在开了客户端 UDP 转发和没开的状态各跑一次，比首屏时间。

结论别走极端：QUIC 在弱网、移动网络、Wi-Fi 与蜂窝频繁切换的场景优势是真实的（丢包不阻塞其他流、换网不断连，这两条 TCP 结构上做不到）；但在带宽充足、丢包极低的场景，性能优势未必抵得过部署复杂度。落到体验上就一句：**链路对 UDP 友好时 QUIC 更快，不友好时 TCP 更稳。**

## 五、服务商说"支持 UDP 转发"，分三档看

既然用户改不了网站的协议，能做的只有让链路尽量放 UDP 走。同样写"支持 UDP"，实现差距非常大：

- **第一档，真 UDP 转发。** 客户端里有独立的 UDP / QUIC 转发开关，打开后游戏、语音、视频通话这类 UDP 业务真的从线路出去。
- **第二档，只做了 TCP。** 只实现了 SOCKS5 的 TCP 部分，UDP ASSOCIATE 没实现或没开。特征是网页浏览一切正常，浏览器 HTTP/3 建不起来，游戏和语音通话却异常。
- **第三档，纯宣传词。** 页面上写着"支持 UDP"，但没有可用开关，或开关点了没反应。

分辨四个动作，按省事程度排：

1. 看客户端里有没有**独立的** UDP / QUIC 转发开关；
2. 开 TUN 模式跑一次 UDP 重业务（游戏延迟、视频通话质量），和不开启对比；
3. 抓包看有没有 UDP 包真的从线路出去；
4. 问客服一个具体问题：**"UDP 转发是 SOCKS5 的 UDP ASSOCIATE，还是 TUN 层透明转发？"** 能答上来并说清差别的，基本可以放心。

## 七、技术现状和三个常见误区

按 APNIC 2025 年发布的全球测量报告，QUIC 的实际使用率已到 70% 左右并仍在增长。代价也真实：HTTP/3 把原先藏在内核协议栈里、不用开发者操心的东西——丢包重传、拥塞控制、流量控制、加密握手——全部摊到用户态和应用层。有个说法很准确：**很多问题不是消失了，而是从"你看不见"变成了"你自己修"。** 服务端要处理 Alt-Svc 降级回退，负载均衡要能识别 QUIC，企业网络要放行 UDP，每一环都是新的运维成本。

三个误区：

- ❌ **"QUIC 就等于更快。"** 收益集中在建连速度、弱网抗丢包、换网不断连。带宽充足、丢包极低的场景它未必更快，甚至因用户态开销更慢。
- ❌ **"开了 HTTP/3 就一定连得上。"** UDP 通不通是链路的事，跟协议本身无关。
- ❌ **"协议换对了什么问题都解决。"** 丢包率到一定程度什么协议都救不回来，先看线路质量再谈协议优化。

## 八、常见问题

**Q1：怎么知道浏览器在不在用 HTTP/3？**
F12 打开 Network 面板，右键表头勾选 Protocol 列，`h3` 就是 HTTP/3；也可访问 `chrome://net-internals/#http3` 看连接明细。

**Q2：同一个网站，家里宽带和公司网络表现差很多，是宽带的问题吗？**
不一定。排查顺序：先排除设备与浏览器（换浏览器、无痕模式），再排除网络出口（切换网络对照），最后才看站点本身。换成手机热点就恢复正常的，问题在原网络的出口策略上。

**Q3：关掉 QUIC 会让上网更快吗？**
看访问什么。目标网站走 HTTP/3 而链路对 UDP 不友好时，关掉让它走 TCP 反而更稳；链路 UDP 正常时关掉只是白丢弱网优势和换网不断连。建议 A/B 一次再决定，别盲目关。

**Q4：为什么网页能打开，游戏和语音通话就是不行？**
典型的分层现象。网页走 TCP，游戏与语音通话大量依赖 UDP。TCP 通、UDP 不通，说明链路上有只放行 TCP 的策略，换协议没用，得换链路。

**Q5：服务商宣传的"QUIC 加速"是什么？**
多数是"支持 UDP 转发 + 线路质量好"的另一种说法，并不是它在帮你加速 QUIC——决定用不用 QUIC 的是网站服务端。当成一条筛选线索即可。

**Q6：IPv6 跟这件事有关系吗？**
有一点。IPv6 环境下没有运营商级 NAT 那一层，UDP 端到端路径更直接，理论上对 QUIC 更友好，前提是路由器和运营商都真的开了 IPv6。

## 九、总结

QUIC 和 HTTP/3 解决的是 TCP 的老问题：握手慢、队头阻塞、换网断连。技术上更现代，弱网和移动场景的优势是真的。

但因为 QUIC 全程走 UDP，它的实际表现取决于脚下这条链路对 UDP 的态度。链路友好它更快，链路不友好它比 HTTP/2 更卡，而且浏览器不会告诉你。

用户控制不了网站用什么协议，能控制的是自己走哪条线路。真正的行动项只有一句：**别只看宣传里的"支持 QUIC"，去看客户端里有没有能用的 UDP 转发，自己跑一次对比。**
